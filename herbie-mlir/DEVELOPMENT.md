# Development Guide for herbie-mlir

This guide walks through the herbie-mlir architecture, build system, and common development tasks.

## Quick Start

```bash
# Clone with submodules
git clone https://github.com/jumerckx/Tamagoyaki
cd Tamagoyaki

# Configure and build (pulls Rival from GitHub automatically)
cmake -B build \
  -DCMAKE_BUILD_TYPE=RelWithDebInfo \
  -DCMAKE_PREFIX_PATH=$PWD/mlir
cd build
ninja

# Run tests
ninja check-herbie-mlir
```

## Project Structure

### `/herbie-mlir/include`

Public headers for herbie-mlir:

- **`HerbieMLIR.h`**: Main header with pass declarations
- **`RivalCAPI.h`**: C API bindings for Rival (interval arithmetic)

These are meant to be the public API surface for users of herbie-mlir.

### `/herbie-mlir/src`

Implementation of MLIR passes and utilities:

- **`HerbieMLIRPasses.cpp`**: Pass implementations

Each pass should:
1. Be declared in a TableGen file (would go in `/herbie-mlir/include`)
2. Implemented here
3. Registered via `#define GEN_PASS_DEF_*` macros

### `/herbie-mlir/rival`

Integration layer for Rival:

- **`CMakeLists.txt`**: 
  - Uses `FetchContent` to pull rival-rs from GitHub
  - Runs `cargo build` to compile Rival's C API
  - Creates `RivalCLib` and `Rival` targets
  - Supports local development mode via `-DRIVAL_ENABLE_LOCAL_DEV=ON`

### `/herbie-mlir/tools`

Command-line tools:

- **`herbie-mlir-opt`**: Optimizer driver (like `tamagoyaki-opt`)

### `/herbie-mlir/test`

Lit-based tests using MLIR syntax:

- Tests use MLIR as the test language
- Follow `// RUN:`, `// CHECK:` conventions from LLVM Lit

## Build System Details

### CMake Integration Strategy

**Why not a submodule?**
- Submodules require explicit clones (`git submodule update`)
- FetchContent is easier for CI/CD and distribution
- Developers opt-in to local mode when they want rapid iteration

**The build flow:**

```
cmake (root)
  └─ add_subdirectory(herbie-mlir)
      ├─ include/CMakeLists.txt (headers)
      ├─ src/CMakeLists.txt (library: herbieMLIR)
      ├─ rival/CMakeLists.txt
      │   ├─ FetchContent_Declare(rival, GIT_REPOSITORY, GIT_TAG)
      │   ├─ add_custom_target(buildRival) → runs cargo build
      │   └─ Creates targets: RivalCLib, Rival
      ├─ tools/CMakeLists.txt (herbie-mlir-opt)
      └─ test/CMakeLists.txt (Lit tests)
```

### Rival Build Options

**Standard (GitHub fetch):**
```bash
cmake -B build \
  -DCMAKE_PREFIX_PATH=$PWD/mlir
```
- Downloads latest `main` branch
- Cargo caches deps in `build/rival/target`

**Local development:**
```bash
cmake -B build \
  -DRIVAL_ENABLE_LOCAL_DEV=ON \
  -DRIVAL_LOCAL_PATH=/path/to/rival-rs \
  -DCMAKE_PREFIX_PATH=$PWD/mlir
```
- Uses local filesystem path
- Changes to Rival source automatically trigger rebuild
- Faster iteration when working on Rival + herbie-mlir together

**Custom fork/tag:**
```bash
cmake -B build \
  -DRIVAL_REPO_URL=https://github.com/you/rival-rs \
  -DRIVAL_GIT_TAG=my-feature-branch \
  -DCMAKE_PREFIX_PATH=$PWD/mlir
```

## Adding a New MLIR Pass

### 1. Define the pass in TableGen

Create `include/HerbieMLIRPasses.td` (if it doesn't exist):

```tablegen
include "mlir/Pass/PassBase.td"

def HerbieIntervalAnalysis : Pass<"herbie-interval-analysis", "::mlir::ModuleOp"> {
  let summary = "Analyze value ranges using Rival interval arithmetic";
  let description = [{
    This pass traverses the IR and annotates operations with interval
    information computed via the Rival library.
  }];
  let dependentDialects = [
    "::mlir::func::FuncDialect",
    "::mlir::arith::ArithDialect"
  ];
}
```

Then update `include/CMakeLists.txt`:

```cmake
set(LLVM_TARGET_DEFINITIONS HerbieMLIRPasses.td)
mlir_tablegen(HerbieMLIRPasses.h.inc -gen-pass-decls)
mlir_tablegen(HerbieMLIRPasses.cpp.inc -gen-pass-capi-header)
add_public_tablegen_target(HerbieMLIRPassesIncGen)
```

### 2. Implement the pass

In `src/HerbieMLIRPasses.cpp`:

```cpp
#include "herbie-mlir/HerbieMLIR.h"

#define GEN_PASS_DEF_HERBIEINTERVALANALYSIS
#include "herbie-mlir/HerbieMLIRPasses.h.inc"

namespace herbie {

namespace {

class HerbieIntervalAnalysisPass
    : public impl::HerbieIntervalAnalysisPassBase<HerbieIntervalAnalysisPass> {
public:
  using impl::HerbieIntervalAnalysisPassBase<
      HerbieIntervalAnalysisPass>::HerbieIntervalAnalysisPassBase;
  
  void runOnOperation() final {
    mlir::ModuleOp module = getOperation();
    
    // Use Rival C API
    #include "herbie-mlir/RivalCAPI.h"
    RivalContext* ctx = rival_context_new();
    
    // Analyze the module...
    
    rival_context_free(ctx);
  }
};

} // namespace

void registerHerbieIntervalAnalysis() {
  // Auto-generated by TableGen
}

} // namespace herbie
```

### 3. Register the pass

Update `include/HerbieMLIR.h` to include the generated file:

```cpp
#define GEN_PASS_DECL
#include "herbie-mlir/HerbieMLIRPasses.h.inc"
```

And in `tools/herbie-mlir-opt.cpp`, register all passes:

```cpp
void herbie::registerPasses() {
  // Generated registration code runs automatically
}
```

### 4. Add tests

Create `test/lit/herbie-interval-analysis.mlir`:

```mlir
// RUN: herbie-mlir-opt -herbie-interval-analysis %s | FileCheck %s

// CHECK-LABEL: func @analyze
// CHECK: some expected output after analysis
func.func @analyze(%arg0: f32) -> f32 {
  %0 = arith.constant 1.0 : f32
  %1 = arith.addf %arg0, %0 : f32
  return %1 : f32
}
```

## Using Rival in Your Passes

The `RivalCAPI.h` header provides C bindings to Rival's Rust code.

### Example: Creating and analyzing intervals

```cpp
#include "herbie-mlir/RivalCAPI.h"

// In your pass:
RivalContext* ctx = rival_context_new();

// Create a rational: 1/2
RivalRational* rat = rival_rational_new(ctx, 1, 2);

// Create an interval [0, 1]
RivalRational* zero = rival_rational_new(ctx, 0, 1);
RivalRational* one = rival_rational_new(ctx, 1, 1);
RivalInterval* interval = rival_interval_from_rationals(ctx, zero, one);

// Perform arithmetic
RivalInterval* doubled = rival_interval_mul(ctx, interval, interval);

// Print
std::string result = rival_interval_to_string(doubled);
llvm::errs() << "Result: " << result << "\n";

// Cleanup
rival_interval_free(interval);
rival_interval_free(doubled);
rival_rational_free(zero);
rival_rational_free(one);
rival_rational_free(rat);
rival_context_free(ctx);
```

### Error handling

For now, the C API returns null on errors. Check before using:

```cpp
RivalInterval* result = rival_interval_add(ctx, a, b);
if (!result) {
  emitError("Interval operation failed");
  return failure();
}
```

## Testing Strategy

### Unit tests

For C++ logic, add unit tests in a separate `test/cpp` directory if needed.

### Integration tests (Lit)

Most tests are Lit-based MLIR tests in `test/lit/*.mlir`:

```mlir
// RUN: herbie-mlir-opt -pass-name %s | FileCheck %s

// CHECK-LABEL: @test
// CHECK: expected pattern after transformation
func.func @test(%arg0: f32) -> f32 {
  // Test input
  return %arg0 : f32
}
```

### Running tests

```bash
# All herbie-mlir tests
ninja check-herbie-mlir

# Single test file
lit test/lit/herbie-interval-analysis.mlir -v

# With debug output
lit test/lit/herbie-interval-analysis.mlir -v -a
```

## Debugging

### Enable verbose Cargo output

```bash
CARGO_VERBOSE=1 ninja buildRival
```

### Inspect generated CMake files

Look in `build/herbie-mlir/` for generated `.h.inc` and `.cpp.inc` files to understand what code TableGen produces.

### Print intermediate IR

In your passes, use:

```cpp
module.dump();  // Print human-readable MLIR

// Or with generic form
OpPrintingFlags flags;
flags.printGenericOpForm();
module.print(llvm::outs(), flags);
```

### Valgrind memory checking

If you suspect memory leaks in Rival integration:

```bash
valgrind --leak-check=full build/bin/herbie-mlir-opt input.mlir
```

## Incremental Development Workflow

### Scenario: Adding a new pass

1. **Define** (`include/HerbieMLIRPasses.td`):
   ```bash
   # Edit table gen, save
   ```

2. **Implement** (`src/HerbieMLIRPasses.cpp`):
   ```bash
   # Edit implementation, save
   ```

3. **Test** (`test/lit/my-pass.mlir`):
   ```bash
   # Write test, save
   ```

4. **Build and verify**:
   ```bash
   cd build
   ninja                              # Rebuilds affected targets
   lit ../test/lit/my-pass.mlir -v   # Run your test
   ```

TableGen regeneration is automatic via CMake. If you hit stale `.inc` files:

```bash
cd build
ninja clean
ninja  # Full rebuild
```

### Scenario: Updating Rival

Working on both Rival and herbie-mlir:

```bash
# Terminal 1: herbie-mlir
cd /path/to/Tamagoyaki
cmake -B build \
  -DRIVAL_ENABLE_LOCAL_DEV=ON \
  -DRIVAL_LOCAL_PATH=/path/to/rival-rs \
  -DCMAKE_PREFIX_PATH=$PWD/mlir
cd build

# Terminal 2: rival (in another shell)
cd /path/to/rival-rs
cargo build  # Develop Rival independently

# Back in Terminal 1:
ninja buildRival  # Rebuilds Rival C lib
ninja             # Rebuilds herbie-mlir against new Rival
```

Changes to Rival source automatically trigger rebuild on next `ninja buildRival`.

For GitHub Actions or similar:

## Troubleshooting

| Problem | Solution |
|---------|----------|
| CMake can't find `RivalCLib` | Ensure `buildRival` custom target ran; check `build/herbie-mlir/rival/CMakeFiles/buildRival.dir/build.log` |
| Cargo compile errors | Check Rust in PATH: `cargo --version` and `rustc --version` |
| Linker errors with Rival symbols | Ensure `RivalCLib` is linked: check `src/CMakeLists.txt` includes `target_link_libraries(herbieMLIR PUBLIC RivalCLib)` if using Rival |
| Stale TableGen headers | `ninja clean` in build dir, then `ninja` |
| Local Rival changes not picked up | CMake caches Rival path; try `cmake --build build --target buildRival` explicitly |

## Architecture Decisions

### Why FetchContent over submodule?

- **CI friendly**: No git submodule update needed
- **Developer friendly**: Local mode via `-DRIVAL_ENABLE_LOCAL_DEV=ON`
- **Distribution friendly**: Sources bundled in artifacts

### Why custom `add_custom_target(buildRival)` over ExternalProject_Add?

- Simpler integration with existing CMake
- Better control over Cargo invocation
- Easier to debug (see actual commands)

### Why separate `RivalCAPI.h` header?

- Clear boundary between C++ and Rust
- Easy to review/update C API surface
- Decouples from actual Rival implementation details
